# 測試套件說明 (Tests)

本目錄是 `antigravity-script-runner` 的**驗證套件**：純 Node、零外部依賴，不需要啟動 IDE 或安裝任何 npm 套件。

---

## 1. 如何執行

```powershell
node tests/run-all.js          # 一次跑完三支（建議）
npm test                       # 同上（package.json 已設好）
node tests/frontend.dom.js     # 只跑前端互動語意
node tests/backend.smoke.js    # 只跑後端面板生命週期
node tests/locales.check.js    # 只跑語系檢查
```

- 全部通過 → 輸出 `ALL-SUITES-PASSED (3/3)`，退出碼 `0`。
- 任一失敗 → 該支輸出 `...-TEST-FAILED (checked=N, failed=M)`，退出碼非 `0`（可直接掛進 git hook / CI）。

---

## 2. 為什麼測「送出的訊息」而不是測「畫面」

本擴充套件的核心是**分頁角色**的切換（檔案分頁 ↔ 資料夾畫廊分頁），而「切換分頁」這件事由**後端**執行、前端只負責在對的情境**送出對的訊息**。

因此測試設計成兩層，各自驗證自己真正負責的部分：

| 層 | 驗證對象 | 手段 |
| :--- | :--- | :--- |
| 前端 | 哪個操作 → 送出哪個訊息、帶什麼參數 | DOM 模擬，觀察 `vscode.postMessage` |
| 後端 | 收到訊息 → 開／關／喚醒哪些分頁、標題與 initData 內容 | mock `vscode` API，觀察 `createWebviewPanel` / `dispose` / `postMessage` |

這正是肉眼最難驗證、也最容易寫錯的地方：**事件接對了嗎？帶對參數了嗎？在錯的分頁情境會不會誤觸？**

---

## 3. 三支腳本各驗什麼

### `locales.check.js`
- zh-TW / en 鍵集合完全對稱（無缺漏、無多餘）、無空字串值。
- `viewer.js` 與 `index.html` 實際引用的 i18n 鍵（`t('key')`、`data-i18n*`）在兩個語系都存在。
- 防的是：新增按鈕卻忘記加翻譯、改了鍵名沒同步。

### `frontend.dom.js`（61 項斷言）
- 三個檢視器（圖片／影片／音訊）的 **檔案分頁**：`Esc`／滑鼠右鍵／✕／`G`／工具列按鈕 → 送出 `expandToFolderGallery` 並帶出目標檔路徑，且**不**送 `closeCustomEditor`。
- 三個檢視器的 **畫廊分頁**：`Esc` 只退出放大檢視、不送任何分頁訊息、不顯示展開按鈕、`revealInGallery` 只定位不放大。
- 音訊專屬：刪除播放中檔案時的行為、`Esc` 優先序。

### `backend.smoke.js`（63 項斷言）
- 開檔（自訂編輯器）**沿用 VS Code 既有分頁**，`initData` 標記 `isCustomEditor` 並帶出 `targetFilePath`。
- 展開後建立標題為「`類型: 資料夾名`」的畫廊分頁、原檔案分頁被關閉、新分頁 `initData` 帶出 `revealFilePath`。
- 同資料夾已有畫廊分頁 → 不重複開分頁，改送 `revealInGallery`（可要求選取）。
- `closeCustomEditor` 守門：畫廊分頁收到時**不得**被關閉。

## 4. 負對照（Negative Control）—— 最重要的一條紀律

**「測試通過」不代表測試有效。** 一段永遠會通過的斷言，只會製造虛假安全感。

因此凡是要**驗證某個修正**（尤其是修 bug），請一律做一次負對照：

1. 先把修正**暫時改回錯誤版本**（或註解掉關鍵那一行）。
2. 重跑測試，確認**對應的那一項會 FAIL**。
3. 還原修正，再跑一次確認全綠。

**實例（本套件真的抓過）**：音訊檢視器刪除正在播放的檔案時，原本會停在已刪除的檔案上。修正為「改播下一首」時必須在 `playTrack()` 前加 `currentIndex = -1`——因為 `playTrack()` 內建「同曲→切換暫停」早退分支，不重設就會被誤判成「使用者點了同一首歌」而只做暫停。

把 `currentIndex = -1` 拿掉後重跑，得到：

```
  FAIL  自動改播下一首 c.flac（修正前會停在已刪除的 b.wav）
FRONTEND-TEST-FAILED  (checked=61, failed=1)
```

若當時沒有做這個動作，就無法區分「測試有效」與「測試剛好沒測到」。

> 另一條同等重要的紀律：**發現可疑現象先驗證再回報**。曾有一次 grep 輸出看起來像程式碼結構損壞（多行 context 交錯印出，出現貌似 `else` 後緊接括號的錯位片段），實際是**工具輸出格式造成的顯示假象**——`node --check` 全數通過即證明檔案無損。若當時直接回報「程式碼損壞」，就會製造一場假警報。

## 5. 覆蓋邊界（測不到的東西，請別誤判為已驗證）

- **DOM 模擬不做版面計算**：所有 `getBoundingClientRect` 都是固定假值，查詢一律回傳傀儡元素。→ **CSS／佈局／溢出／對齊類問題一律測不到。**
- **不做事件冒泡**：需以 `_fire()` 直接觸發監聽器（測試中已明確標註「掛在 document 上」等實際綁定位置）。
- **mock vscode 不是 VS Code**：無法重現真實的分頁重用策略、Webview 重建（`retainContextWhenHidden`）、`reveal()` 的欄位行為。
- 因此：**任何 UI 改動在提交前，仍建議在真實 IDE 做一次煙霧測試**（雙擊開檔 → 右鍵退出 → 再雙擊開檔）。

---

## 6. 新增測試案例的規範

1. **可攜路徑**：一律以 `__dirname` 推導（`path.join(__dirname, '..')`）；測試素材放 `os.tmpdir()`。**嚴禁**寫死本機絕對路徑。
2. **自我清理**：建立的暫存檔／目錄要刪除；若測試會啟動長駐服務（如本套件的串流伺服器），收尾必須呼叫 `extension.deactivate()`，否則 Node 行程不會結束（曾發生）。
3. **等待用輪詢、不用固定 sleep**：`waitFor(predicate, timeout)` 可避免慢機器上的偽陰性。
4. **斷言訊息要能自我解釋**：寫「修正前會發生什麼錯誤結果」，而不只是「應該等於 X」。例：`'自動改播下一首 c.flac（修正前會停在已刪除的 b.wav）'`。這讓未來失敗時不必回頭讀原始碼就能判斷影響。
5. **一個案例驗一項行為**：避免「一個斷言同時檢查三件事」，否則失敗時無法定位。
6. 新增功能時**同步補測試**；若行為是刻意的取捨（例如某分頁只定位不放大），也請用斷言把它固定下來，避免日後被無意改動。
